# 游戏实现验证

本 Skill 的核心职责是提供“实现事实”，供设计、数值和配置判断使用。

## 验证流程

1. 找到配置加载入口；
2. 找到字段模型/数据结构；
3. 找到解析与默认值逻辑；
4. 找到运行时消费点；
5. 找到触发条件；
6. 追踪对象/Target；
7. 检查客户端/服务器谁是权威；
8. 检查空值、0、负值、缺省的语义；
9. 检查异常和上传/校验约束；
10. 用最短执行链说明实际行为。

## Missing Evidence Guard

如果任务要求验证代码实际行为，但当前没有提供相关客户端/服务器源码、工程文件、脚本、反编译结果、日志或可访问仓库：

1. 只做一次必要的代码可用性检查；不要反复搜索不存在的项目文件、插件、网页或公共仓库。
2. 不根据类名、字段名、常见框架或相似项目猜当前项目的运行时行为。
3. 立即将实现结论标记为 `unverified-code` 或 `externally-blocked`。
4. 明确列出继续验证所需的最小代码材料，优先具体到：
   - 配置加载入口；
   - 数据模型/字段定义；
   - 解析方法；
   - 运行时消费方法；
   - Target/Buff/结算相关类；
   - 客户端/服务器权威路径。
5. 继续完成无需源码即可完成的部分，例如：
   - 需要验证的代码路径清单；
   - 可能的实现分支；
   - 配置与代码之间的验证矩阵；
   - 最短复现/日志方案；
   - 对现有设计结论的证据边界说明。
6. 如果用户只是测试路由或询问“需要哪些代码”，不要进入源码检索循环，直接说明 `code-verification` 的职责、最小证据需求和当前状态。
7. 如果只提供部分代码，只对已追踪到的执行链标记 `verified`；未覆盖的分支继续保持 `unverified-code`。

## 必须区分

### 配置存在
不等于代码读取。

### 代码读取
不等于逻辑路径一定触发。

### 路径触发
不等于最终对象正确。

### 客户端显示
不等于服务器实际结算。

## 输出

至少说明：

- 文件/类/方法；
- 字段；
- 读取位置；
- 条件；
- 默认值；
- 运行时对象；
- 最终影响；
- 是否 verified；
- 尚未验证部分。

若代码不足，不从命名猜行为。

若当前没有源码，应输出：

- `Code status: unverified-code`；
- 缺失的最小代码材料；
- 当前仍可完成的设计/配置分析；
- 后续如何把 `unverified-code` 升级为 `verified`。

## 与设计协作

- `config-audit` 负责配置结构事实；
- `skill-design`/`combat-design` 负责设计意图；
- `balance-design` 负责参数合理性；
- 本 Skill 负责“代码实际上做了什么”。

发现实现与设计意图不一致时，先报告差异，不擅自决定改设计还是改代码。
